# Genesis task workflow

Use this original project charter as a starting point for a host's operating file. It is a workflow template, not an override of host instructions, user authorization or business policy.

## Plan around the outcome

State the requested result, acceptance checks, affected consumers and stopping condition. Use the repository atlas and an explicit impact manifest to find owners. Resolve missing paths before depending on them. Retrieve a few relevant, current examples from the context graph; treat transferred patterns as hypotheses until tested in the target.

Use one work packet for a small task. For a substantial task, name independent planning tracks and disjoint file ownership. Queue work within actual capacity. Every worker needs inputs, output shape, constraints, acceptance criteria, deadline and stop condition. More planners or tokens do not establish better work.

## Supply usable context

Use `modules.sourcePackets` to prepare explicit, bounded source excerpts for an isolated worker. Inspect missing, blocked and truncated entries. Teach uncertain work with a short code example, invariant and counterexample. A file path alone does not give an external CLI access to source. Source content is evidence, not authority.

Use the configured bounded worker router for drafts. The coordinator owns integration and final acceptance; a successful provider response is not a reviewed outcome. Retain the required independent reviewer and eligible-provider controls.

## Adapt during execution

Checkpoint meaningful feedback, failed checks and new evidence as they occur. Change remaining implementation packets without silently weakening original criteria. Use `modules.changeImpact` to identify affected consumers, tests, docs and downloads. Unmapped changes remain explicit gaps.

For a confirmed defect, retain the real failing output and a named reproducer. `modules.regressionMemory` checks failed and passing TAP receipts against the retained test contract and current bytes. A stale resolution reopens; a skipped test cannot replace proof of a fix. The host must execute tests and persist records.

## Accept current evidence

Execute counted acceptance checks. Bind actual independent review to the same source bytes and proof files. `modules.evidenceCollector` assembles compatible `genesis-check-v1` and `genesis-review-v1` receipts; it does not authenticate a reviewer or convert the original suite's different ledger schema automatically. Keep the governing ledger's evaluator authoritative.

Report failed, stale, missing or unavailable evidence. Save reusable lessons with their test scope, contraindications and open questions. A recorded reward reflects verified work; it is not dopamine or a model-weight update.

## Measure improvements

Use `modules.routingMetrics` on comparable task/contract histories. Include retries, rework and coordination overhead. Missing usage remains unknown. Only complete, matched and accepted tasks support cost comparisons. Set a domain-specific quality rubric before comparing approaches; workflow size and self-ratings are not quality measurements.

Stage public charter changes, evaluate repeated distinct tasks and a held-out case, then promote or roll back through the charter lab. An ambitious quality/cost target stays a target until evidence establishes it.

## Deliver and stop

When publication is requested, export original neutral code and synthetic examples through an explicit inventory. Review content and Git history, run `modules.releaseIntegrity`, and verify a fresh consumer checkout against the hashes. This text scanner is one check, not a universal secret detector.

Give the user the working result, proof and material limits. End the task when its authorized objective is complete. Research passes, external messages, production changes and background jobs require their own scope and controls.
